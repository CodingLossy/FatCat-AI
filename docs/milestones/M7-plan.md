## 2. 各 PR 的验收标准

### PR 2 · `feat/plugin-core`

1. 清单 zod schema 在 `packages/shared`(Apache-2.0),未知字段、越界路径、过宽的 `net:` 域名范围(`*.com`)、缺字段全部给出稳定的中文原因码。
2. 本地目录安装:预览不产生任何副作用(预览后数据目录与数据库不变);同意的权限集合与清单不一致时安装被拒绝。
3. 升级时新增权限 → 进入 `disabled` 等待重新同意;权限不变 → 直接启用。
4. 卸载流水线按 ADR 0040 第 9 节执行:快照对比测试(数据库相关表行数、数据目录文件树)通过;`removing` 状态重启后能继续;勾选保留数据时数据移到 `plugins/.kept/`。
5. 设置表单:`secret` 项不回显,存入加密存储,卸载时一并删除。
6. 没有安装任何插件时,CI 空闲 RSS 门禁通过(贴出前后实测);管理器模块按需加载。
7. OpenAPI 已同步,oasdiff 无破坏性变更;Web 插件页中英文案齐全,附每个界面的截图。

### PR 3 · `feat/plugin-mcp`

1. 用仓库自带的假 MCP 服务器做成插件:安装 → 启用 → 工具 `plugin.{id}.{tool}` 出现在 `GET /tools`(`source = 'plugin'`)→ 调用需要审批 → 停用后工具消失。
2. 子进程环境变量**只含**设置项映射和最小基础集;清单里写 `FATCAT_AI_*` 或要求取宿主环境变量的写法被拒绝(🔒 测试)。
3. 风险下限:声明 `read` 但带 `fs.write` / `net:` 的工具被抬到 `write`;`sendsData` 的工具是 `external`,请求 `remember` 返回 400;`dangerous` 的声明被拒绝。
4. 卸载后 `plugin.{id}.` 前缀的预授权全部删除并有审计。
5. 外连清单出现该插件声明的域名,标为「声明,未强制」,`check:egress` 与运行时一致性测试通过。
6. 终止:停用 / 卸载后无残留子进程;Windows 上杀进程树(业主真机验证)。

### PR 4 · `feat/plugin-install-sources`

1. 本地假 npm registry 与假 GitHub 归档服务做集成测试:完整性不符 → 拒绝;`dist.integrity` 与归档不符 → 拒绝。
2. 安全解包的 🔒 用例:符号链接、硬链接、`..`、绝对路径、Windows 保留名、文件数 / 体积 / 压缩比超限,各一条,全部整体回滚、不留残留文件。
3. 宿主不会调用 `npm` / `git` / 任何生命周期脚本(测试里把它们放进 `PATH` 作为陷阱,被调用则失败)。
4. GitHub 来源把标签解析成 40 位提交并在预览中展示;安装记录只存提交哈希。
5. 升级:保留上一版本,失败可回滚;新版本启动成功后清理更早版本。
6. 外连清单加入 `registry.npmjs.org`、`codeload.github.com`;fake-IP 开关对安装器生效。

### PR 5 · `feat/plugin-native-runtime`

1. **闸门**:三平台实测报告(放进 PR 描述):`--permission` 的读 / 写允许列表是否按预期生效,Node 自身运行库是否需要额外放行。不通过按问题 3 处理。
2. 隔离 🔒 测试(在真实子进程里跑):读 `secrets.yaml`、`master.key`、`db.sqlite`、`process.env.FATCAT_MASTER_KEY` 全部失败 / 为空;`child_process.spawn`、`worker_threads`、加载 `.node` 扩展失败;写 `data/` 之外失败。
3. 宿主 API 越权 🔒 测试:未授权的 `net:` 域名、授权目录之外的路径、被 net-guard 拦截的地址(含 IPv4 映射的 IPv6)、未授权的 `items.provide` 各返回 `permission_denied` 并写审计。

## 7. 安全要点(评审时对照)

1. 插件**从不**获得 `secrets.yaml` / `master.key` / `db.sqlite` 的访问(原生:进程权限;MCP:环境变量不传 + 文档如实说明文件系统不受限)。
2. 权限只是上限,审批与预授权不被绕过;`external` 不可预授权。
3. 不运行包管理器和安装脚本;解包整体回滚。
4. 插件不能向 Web UI 注入脚本。
5. 校验和只防「内容被换」,不防「审核通过了恶意插件」,文档写明。
6. 所有插件输出都是不可信内容。

## 9. 待业主决定的问题(每条先写推荐;不回复就按推荐做,例外见本节末尾)

1. **原生插件默认开还是关?** 推荐:**默认关闭**,设置里「允许原生插件」打开时有风险确认文案。理由:Node 权限模型挡不住直接联网(ADR 0040 第 5.2 节),默认关闭让只用 MCP 的用户没有额外风险。
2. **Git 来源的范围。** 推荐:M7 只支持 **GitHub + 固定提交**,npm 只支持**精确版本**。理由:用 `codeload.github.com` 取归档不需要 `git`,Docker 镜像里没有 git;范围小,校验简单。其他 Git 主机以后再说。
3. **如果 Node `--permission` 在 Windows 上实测不可靠怎么办?** 推荐:**原生插件推迟,M7 先交付 MCP 插件**(PR 5 缩小为占位与说明),验收「一个 MCP 插件 + 一个原生插件」改为只验 MCP,并把原生部分写进 M7.1。理由:没有可靠隔离就开放原生插件,等于安全承诺落空。
4. **市场索引仓库叫什么、谁来建?** 推荐:`CodingLossy/fatcat-plugins`,**由业主创建**(创建仓库不是 C 能代办的事),C 在 PR 7 提供模板与 CI 脚本。仓库建好之前 PR 7 用本地假索引开发。
5. **渠道插件(`registerChannel`)做不做?** 推荐:**M7 不做**,ADR 0040 只保留权限名 `channel.provide`。理由:渠道涉及绑定、群聊注入、敏感度、审批推送(ADR 0022)和注入评测,体量接近一个单独的小里程碑;不影响 M7 验收。如果要做,作为 M7 之后的 PR,先写设计 ADR。
6. **插件能不能读记忆 / 知识库 / 邮件?** 推荐:**M7 都不开放**(权限表里没有这些项)。理由:这几项直接关系「不可信内容进记忆」与「发送一律审批」的底线;需要时再逐项开放,每项单独写 ADR 并加评测。
7. **插件更新。** 推荐:**只手动「检查更新」**,不后台轮询、不自动安装。理由:零遥测承诺,且升级可能新增权限。
8. **安装插件要不要二次验证(TOTP)?** 推荐:**TOTP 已启用时要求**,没有启用就只要登录 + CSRF;PR 2 先核对 ADR 0027 现有机制能否复用,不能复用就只做登录 + CSRF 并在 PR 描述里说明。
9. **原生插件的运行参数。** 推荐:按需启动、空闲 5 分钟退出,同时最多 3 个,每个 `--max-old-space-size=64`;都可在设置里调整。理由:2 GB 机器上更保守。
10. **`toolSet`(任务确认卡声明所需工具集合)何时做?** 推荐:**在 PR 3 之前单独做**(ADR 0039 第 4 节评估过,无迁移),这样无人值守任务可以按 `plugin.{id}.` 前缀限定插件工具。如果不先做,插件工具默认不进无人值守任务的建议集合,风险可控,M7 也能继续。
11. **原生插件与 AGPL 的措辞。** 推荐:文档写「原生插件通过进程边界和公开的 JSON-RPC 协议与核心通信,SDK 为 Apache-2.0,插件作者自选许可证」,但这是法律立场,**请业主确认措辞(必要时咨询律师)后再发布到文档站**;PR 8 在得到确认前不合并该段。
12. **何时把 `@fatcat-ai/plugin-sdk` 发布到 npm?** 推荐:PR 8 里只做发布准备(`private` 保持 true),**由业主决定发布时机**;SDK 0.x 期间可以不兼容地调整,1.0 起遵守 `pluginApi` 稳定性承诺。
13. **工具风险下限规则是否合适。** 推荐:ADR 0040 第 4 节的规则——无权限可 `read`,`fs.write` / `net:` 下限 `write`,`sendsData` 为 `external`,默认 `write`,`dangerous` 不接受。如果觉得对 `net:` 过严(例如纯查询天气也要审批),可以允许插件作者声明 `read` 并由用户在安装界面单独确认「这个工具会联网读取,但不上传你的数据」。

**需要业主明确同意才能做**(不会因为不回复而自动执行):合并(含数据库迁移的 PR 2、PR 5 由业主亲自确认并合并)、创建市场索引仓库、发布 SDK 到 npm、改动数据目录或真实数据、安装任何真实第三方插件、打 tag / 发 Release、推送镜像。
