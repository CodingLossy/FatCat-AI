## 0. 范围

在 M6:

1. **任务模型**:触发器(cron、一次性时间、事件:新邮件、文件变化、Webhook)+ 动作(一段提示词交给 Agent,或固定工具链)+ 输出去向(会话、微信渠道推送、邮件)。

## 2. 任务模型(ADR 0033,PR 2 写)

### 2.1 概念

一个**任务**(`Task`)= 名称 + 触发器 + 动作 + 输出去向 + 策略(重试、静默、错过策略、预授权)+ 启用开关。任务属于主人(`ownerId`,1.0 单用户)。

| 部分     | 取值                                                                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 触发器   | `cron`(5 段表达式 + 用户时区,croner)、`once`(一个绝对时刻,存 UTC 与创建时的时区)、`event:mail.received`(PR 4)、`event:file.changed`(PR 4)、`event:webhook`(PR 4)。一个任务一个触发器;多个触发器就建多个任务。 |
| 动作     | `agent_prompt`:一段提示词交给 Agent,在**独立的任务会话**里运行(PR 3);`tool_chain`:固定的工具调用序列,不经过模型(PR 3);`system`:内置系统任务(维护、`memory.sleep`),不可由用户新建或改动动作,只能启停和改时间。 |
| 输出去向 | 可多选:`conversation`(写入任务会话,Web 可看,默认)、`channel`(推到某个微信渠道,经 `channel.push` 与审批,PR 3)、`mail`(发邮件,经 `mail.send` 与审批,PR 3)。无输出去向的任务只留运行记录与任务会话。             |
| 策略     | `retry`(最大次数、间隔)、`quietHours`(起止时刻 + 静默期间的行为)、`misfire`(`skip` / `catchUp`)、`maxRuntime`、`allowedTools`(预授权白名单,第 4 节)。                                                         |

### 2.2 固定工具链(`tool_chain`)

JSON 数组,每步 `{tool, args, as?}`;后一步的参数可以引用前面步骤的结果(`{{steps.name.result.field}}` 的简单替换,**只做字符串 / 字段替换,不做表达式求值**,不执行任何脚本)。每一步都走与 Agent 完全相同的工具策略与审批:`read` 直接执行,`write` 需审批,`external` 每次审批。链中任何一步被拒绝或过期,整个运行标为 `blocked`,后面的步骤不执行。链长上限 10。

固定工具链只是「不要模型也能做的事」(例如 `mail.list` → `channel.push`)。它不是工作流引擎,M6 不做分支、循环、条件。

### 2.3 触发器细节

- **cron**:5 段;不支持秒级;下次触发时间由 croner 在用户时区计算;改时区后所有 cron 任务立即重新排期(ADR 0023 第 5 节);夏令时沿用 croner 11 的行为。最小间隔 1 分钟(超过就按 1 分钟校验失败),建任务时校验表达式并显示未来 3 次触发时间。
- **once**:绝对时刻;执行后任务自动标为 `completed` 并停用;已过期的 once 任务按 `misfire` 处理(`catchUp`:启动后立即补跑一次;`skip`:标为 `missed`)。
- **事件**(PR 4):
  - `mail.received`:`packages/mail` 同步到新邮件时发内部事件(只带邮件 id、账户 id、文件夹),可按账户、文件夹和发件人精确匹配过滤;**不按正文关键词过滤**(正文是不可信内容,不参与路由)。
  - `file.changed`:只监听已授权目录(`fs_roots`)内的路径;用 Node 内置的 `fs.watch`(不加依赖),按路径去抖(默认 5 秒合并),单次事件批最多 50 个路径;Windows 上 `recursive` 行为不同,列入真机清单。
  - `webhook`:`POST /api/v1/hooks/{taskId}`(**不走会话认证,走任务专属令牌**,见第 8 节);请求体只当作不可信数据交给 Agent,最大 64 KiB。
- **防回环**:任务产生的事件(例如任务写文件触发 `file.changed`、任务发的邮件被同步回来触发 `mail.received`)不触发同一个任务;每个事件触发有**每任务速率上限**(默认每小时 12 次,超出丢弃并在运行记录里记一行 `throttled`)。

### 2.4 运行语义

一次运行(`TaskRun`)的状态机:

```
queued → running → succeeded
                 → failed(可重试 → queued,次数用尽 → failed)
                 → blocked(等待审批被拒绝或过期)
                 → skipped(静默时段、并发满且丢弃、错过策略为 skip)
                 → cancelled(用户取消或服务器关闭)
```

- **并发限制**:全局默认 2 个任务同时运行(`task.maxConcurrency`,1–4);单个任务同一时刻最多 1 个运行(上一次没结束,新的触发按 `overlap` 策略:默认 `skip`,记一行)。超出全局并发的运行排队,队列上限 20,满了丢弃最旧的并记 `skipped`/`queue_full`。**同一时刻最多一个 LLM 密集型任务**(`agent_prompt` 与 `memory.sleep` 共用一个信号量),避免在 2 GB 机器上并发多个模型调用的内存叠加。
- **系统忙时**:若有用户正在聊天(沿用现有 `isBusy`),系统任务与低优先级任务推迟,与现有维护任务的行为一致。
- **重试**:仅对「可重试的失败」(模型超时、网络错误、`postponed`)重试;默认最多 3 次,间隔 1 / 5 / 15 分钟(指数退避带抖动);审批被拒绝 / 过期、配置错误(例如渠道已停用)**不重试**。重试不改变「这次触发」的 id,记录在同一个 `TaskRun` 的 `attempt` 上。
- **静默时段**:任务级别可设(如 22:00–07:00,按用户时区,可跨午夜)。静默期间到点的运行按策略 `defer`(默认:推迟到静默结束后第一时刻运行一次,多次合并为一次)或 `skip`。静默时段**只管「何时执行」**,不改变审批:静默期间产生的审批请求照常发出,但**任务自己不会因此在夜间打扰**——`channel` 输出在静默期间推迟到静默结束(它本来就要审批)。
- **错过策略**(服务器关闭或休眠时错过的触发):
  - `skip`:只记一行 `missed`,等下一次;
  - `catchUp`:启动后补跑**一次**(不论错过了几次),并带上 `scheduledFor`(原定时刻)让动作知道是补跑;
  - 默认:`cron` 任务 `skip`,`once` 任务 `catchUp`,系统维护任务 `catchUp`(与现状一致:启动 10 分钟后补跑当天未完成的)。
  - 补跑上限:启动后 10 分钟内按 `scheduledFor` 排序逐个入队,**不会一次性全部并发**;最长错过窗口默认 24 小时(更久的当 `skip`)。
- **取消**:用户可在 Web 取消排队或运行中的任务;服务器关闭时运行中的任务标为 `cancelled`,不恢复(与审批一致,ADR 0010 第 5 节)。
- **最长运行时间**:默认 10 分钟(`agent_prompt`)、30 分钟(`system`);超时中止并标 `failed`(`timeout`)。

### 2.5 运行记录只存元数据

`task_runs` 存:运行 id、任务 id、触发原因(`schedule` / `catch_up` / `manual` / `event` / `retry`)、`scheduledFor`、开始 / 结束时间、状态、`attempt`、错误码(枚举:`timeout`、`model_error`、`approval_rejected`、`approval_expired`、`output_failed`、`config_error`、`throttled`、`cancelled`、`internal`)、关联的任务会话 id 与 run id、输出去向各自的结果(`sent` / `pending_approval` / `rejected` / `failed`)。**不存提示词全文之外的内容:不存模型输出、邮件正文、Webhook 请求体、错误堆栈**(模型输出在任务会话里,受会话的删除与脱敏规则管理)。保留:每任务最近 200 条,超出的由每日维护清理,与 ADR 0007 第 5.9 节「元数据而已」的原则一致。

## 3. 通用调度器与维护任务迁移(PR 2)

### 3.1 设计

- **位置**:新增 `packages/scheduler`(纯逻辑:排期计算、状态机、并发与重试、静默与错过判定;**不依赖数据库与 croner 以外的任何包**,时间与存储通过注入的接口,便于假时钟测试);`apps/server/src/scheduler-setup.ts` 接存储、`RunManager`、渠道与邮件。存储仓储放 `packages/storage`(「其他包不得自己打开数据库」)。
- **持久**:任务存 `tasks` 表;启动时读出所有启用的任务重新排期。**不持久化「下一次触发时间」之外的内存状态**:每个 `task_runs` 行先写再执行,崩溃后启动时把 `running` / `queued` 的行标为 `cancelled`(`internal: restart`),再按错过策略处理。
- **时钟**:单个 `setTimeout` 链到「最近的下一次触发」,而不是每个任务一个 croner 定时器(任务多时省内存与句柄);用 croner 只做「给定表达式与时区,下一次是什么时候」的计算(`new Cron(expr, {timezone}).nextRun(from)`,不启动其内部定时器)。设备休眠醒来后用 `Date.now()` 与 `scheduledFor` 比较识别错过。
- **时区**:唯一来源是 `Settings.timeZone`(ADR 0023);任务不存自己的时区,只有 `once` 记录创建时的时区用于展示。时区变更事件触发全部重新排期。
- **并发 / 重试 / 静默 / 错过**:第 2.4 节。

### 3.2 维护任务迁移

现有行为的**等价迁移**,不改变维护本身:

| 现在(`maintenance-setup.ts`)          | 迁移后                                                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| croner 每天 03:30 触发 `runAll`       | 系统任务 `system.memory.maintenance`,cron `30 3 * * *`,`misfire: catchUp`                                         |
| 系统忙时推迟,10 分钟后重试,最多 12 次 | 动作返回 `postponed` → 可重试失败,间隔 10 分钟固定、最多 12 次(系统任务的专用重试策略,不走用户任务的 1/5/15 分钟) |
| 启动后 10 分钟补跑当天未完成          | 系统任务的 `catchUp`:启动后 10 分钟入队(与现状一致);「同一天不跑两次」仍由各维护任务自己的日期键保证              |
| 改时区立即 `reschedule`               | 时区变更事件重新排期;`MaintenanceScheduler` 的 `reschedule` / `nextRun` / `runNow` 保留为薄包装                   |
| 无运行记录                            | 每次运行写 `task_runs`,Web 可见                                                                                   |

迁移的**回退办法**:PR 2 保留旧的 `startMaintenance` 的导出与测试一个版本(标注 deprecated),`maintenance-setup.test.ts` 的用例全部通过新实现;若发现退步,可以只回滚 PR 2 的合并(迁移 0016 只新增两张表,见第 5 节)。

## 4. 安全(PR 3 为主)

本节是评审重点。原则:**无人值守不降低任何一条现有保护;任务只能让「自动执行」更保守,不能让它更宽松**。

1. **审批策略不变**。任务中的每次工具调用走与聊天完全相同的 `policy.ts`:`read` 自动,`write` 需审批,`external` / `dangerous` 每次审批、不可预授权(ADR 0010 第 3 节)。任务**没有**自己的「免审批」后门,也不新增新的预授权类型。
2. **无人值守时的审批**:审批请求照常发出(Web 弹窗;若任务输出去向或主人绑定了微信渠道,则推「需要确认」到微信,ADR 0022 第 6 节);30 分钟没人处理按过期 = 拒绝,运行标为 `blocked`(`approval_expired`),**不执行**。重启后待审批失效(ADR 0010 第 5 节)。这是 fail-closed:夜里没人看,什么对外的事都不会发生。
3. **预授权白名单(`allowedTools`),默认空**:
   - 任务可以声明一个工具白名单,**只能列 `read` / `write` 级别且 `preauthorizable` 的工具**,并且可带 ADR 0010 的约束(`pathPrefix`、`domain`)。含 `external` / `dangerous` 工具的白名单在服务器端校验时 400 拒绝。
   - 白名单是**任务级预授权**:只在这个任务的运行里生效,不写入全局预授权表;任务被删除、停用或白名单被改,立即失效;每次使用写审计(`via task <id>`)。
   - 默认为空;Web 的任务编辑页上默认不展示,放在「高级」折叠里,并写明「白名单中的工具在无人值守时会直接执行」。
   - 创建或修改白名单本身是**需要主人在 Web 上明确确认的操作**(自然语言创建路径不能一步带上白名单,见第 5 节)。
4. **发邮件、发渠道消息一律走审批,不能绕过**:
   - 输出去向 `mail` 调用 `mail.send`,`channel` 调用新增的 `channel.push`,二者都是 `external`,**每次都弹审批**,不可预授权,不接受 `allowedTools`。
   - `channel.push` 的新契约(写进 ADR 0033,并修订 ADR 0022 第 7 节「主动推送只有三类」为四类):风险级别 `external`;**目标只能是主人自己已绑定的私聊**(渠道 id 来自任务配置,且必须是 `enabled` 的渠道,目标固定为该渠道的主人会话),**不接受模型或 Webhook 提供的目标**;1.0 仍不提供「发给任意联系人」的工具。内容经渠道降级与切段(ADR 0022 第 7 节),并按渠道过滤:`sensitivity ≥ 1` 的记忆与来源不进入推送内容(与群聊 / digest 的现有规则一致,评测覆盖)。
   - 审批摘要里显示**目标渠道与将要发送的内容预览**(纯文本,不渲染 Markdown),不可信内容照例当数据显示。
   - 同一次运行里,同一输出去向的 `external` 调用最多 1 次(防止模型在任务里循环发送);再次调用直接拒绝,写运行记录 `output_failed`。
5. **不可信内容**:邮件、网页、Webhook 请求体、文件内容进入任务运行时,与聊天里的规则一致(ADR 0016):标记为不可信,不能改变工具集、不能触发 `external` 之外的任何绕过;**会话级「读过不可信内容后条件预授权失效」同样适用于任务会话**。事件触发的任务,其「触发内容」(邮件正文摘要、Webhook 体)默认**不放进系统提示词**,只作为用户消息里的 `<untrusted>` 数据块(沿用现有包装)。
6. **任务会话与提示词的来源**:任务的提示词只能由主人经 Web / API 创建或修改(需要会话认证,TOTP 开启时同样生效)。事件内容、邮件、Webhook 请求体**永远不能创建或修改任务**,也不能修改白名单;自然语言创建只产出「草稿」,草稿由主人确认(第 5 节)。
7. **速率与成本护栏**:每任务事件触发速率上限(第 2.3 节);全局每日 `agent_prompt` 任务运行次数上限(默认 50,可配,0 = 不限);达到上限后新触发记 `throttled`,Web 的任务页顶部显示提示。每次任务运行的模型调用走现有 `chat` 配额与 `usage` 记录。
8. **审计**:任务的创建、修改、启停、删除、手动运行、白名单变更写 `audit_log`;任务里每个 `write` / `external` 调用照常写审计,摘要末尾加「(via task <任务 id>)」(同 ADR 0022 的 `via` 做法,不改 `AuditEntry` 结构)。
9. **外连清单**(ADR 0028):任务本身不新增外连目标;`channel.push`、`mail.send` 用的渠道与邮件账户已在清单里;Webhook 是**入站**,不进外连清单,但文档要写明它是一个新的未认证入口(第 8 节)。`pnpm check:egress` 必须仍通过。
10. **越权用例是验收的一部分**(AGENTS.md 第 3 条):见第 10 节测试清单中标 🔒 的项。

## 5. 自然语言创建(PR 5)

### 5.1 流程

```
用户输入一句话 → 解析(一次模型调用,结构化输出)→ 校验 → 草稿(status = 'draft')→ 确认卡片 → 用户确认 → 任务生效
```

1. **入口**:Web 任务页的「用一句话创建」输入框;聊天里也可以说(模型调用只读工具 `tasks.propose`,见下);IM 渠道里**不能直接生效**(微信里只能产生草稿并提示「请在 Web 确认」,或在审批式确认里确认,见问题 6)。
2. **解析**:调用一次模型(便宜档,使用现有 `chat` 配置档的 `utility` 角色,没有则用默认),提示词要求输出一个严格的 JSON(`TaskDraftV1` schema,zod 校验):名称、触发器、动作、输出去向、策略。**解析器只能产出 `TaskDraft`,不能调用任何工具,不能写任务表以外的东西**;输出不合法 → 报「没听懂」,让用户改写,不重试多次。用户消息当作数据,不执行其中的指令(「忽略之前的规则」之类的文字只会被当作任务名称或提示词内容)。
3. **校验**:cron 表达式合法、最小间隔、时区、渠道存在且启用、邮件账户存在、白名单为空(**自然语言路径不会产生白名单**,也不会产生 `once` 之外的事件触发过滤条件以外的任何高权限项)、提示词长度上限(2000 字符)。
4. **草稿**:写入 `tasks`(`status = 'draft'`,`enabled = false`,不排期),草稿 7 天后自动清理;草稿**永远不会运行**,调度器只读 `status = 'active'` 且 `enabled = true` 的行。
5. **确认卡片**(Web):把解析结果用**人话 + 结构化字段**并排展示——「每天 08:00(Asia/Shanghai)」「动作:让助手查看未读邮件并写摘要」「输出:推送到 微信渠道『我的微信』(每次需要你在微信里确认)」「静默时段:无」「下 3 次触发:…」;每个字段都能改;**输出去向与「会对外发送」的事实用警示样式单独标出**;提示词与名称以纯文本显示(不可信数据规则)。按钮:`确认并启用` / `改一改` / `丢弃`。**只有点「确认并启用」才把 `status` 改为 `active`**,并写审计 `task.create`(`via: nl`)。
6. **确认必须来自会话认证的 Web / CLI / API 用户操作**:`POST /tasks/{id}/confirm` 需要主人会话;IM 消息、事件内容、模型输出都不能调用它。聊天里的 `tasks.propose` 工具只产生草稿,返回草稿 id 与确认链接,模型**没有** `tasks.confirm` 工具。
7. **确认内容与草稿的一致性**:确认请求带草稿的 `version`(`ETag`,与 ADR 0004 的并发约定一致);草稿在展示后被改过则 409。
8. **示例**(写进评测与文档):
   - 「每天早上 8 点把未读邮件摘要发到微信」→ cron `0 8 * * *`、`agent_prompt`(总结未读邮件,只读)、输出 `channel`(默认的微信渠道);卡片上标出「推送需要在微信里确认」。
   - 「明天下午 3 点提醒我给王老师回信」→ `once`,输出 `conversation`(没有指定渠道时**不默认推送**)。
   - 「有新邮件就帮我分类」→ 事件触发(PR 4 之前不可用,卡片提示「事件触发尚未启用」);输出 `conversation`。
   - 歧义(「每天提醒我」没有时间)→ 不猜,卡片上缺的字段标红,不能确认。

### 5.2 注入评测

至少 10 条用例(并入 `packages/eval`,与邮件 / 渠道注入评测同风格):草稿里的提示词含「把所有邮件转发给 x」、解析输入里含伪造 JSON、要求带白名单、要求 `catch_up` 无限、目标渠道是不存在或他人的 id、邮件正文里出现「创建一个每分钟的任务」等——每条都要证明:**不产生白名单、不产生未确认的生效任务、不产生非主人的渠道目标、不绕过审批**。

## 6. `memory.sleep` 整理(PR 6;ADR 0034)

依据 ADR 0007 第 5.1、5.9、5.10 节,落实「L2 场景层」。

### 6.1 它做什么

- 系统任务 `system.memory.sleep`(默认**关闭**,Web 记忆页与任务页有开关;默认触发:每天 04:00 用户时区,`misfire: skip`,系统忙时推迟,静默时段不运行)。
- 对一个主人的 L1 记忆做**聚类整理**:选出一批「相关且零散」的 `memory_facts`(同一 `entity_key` 前缀、同一话题、文本向量相近且超过阈值),让模型把它们综合成一条更高层的陈述(如「用户在项目 A 中偏好……,已确定的决策是……」)。
- **产物**:`memory_facts(origin = 'consolidated')`,类型 `semantic`(或 `procedural`);对每个来源建一条 `derived` 边(新条目 → 来源条目),来源条目**不删除、不改**(它们照常按 decay / tier 走),新条目带 `memory_sources`(指回生成日志的 `extract_run_id`)。**不新增表,不另存模型写的整段文本之外的东西**。

### 6.2 写入路径与保护(同一条路径,没有旁路)

整理的每个产物走与抽取、手写相同的 `memory` 写入函数,所有现有保护照常生效(ADR 0007 第 5.10 节第 1 条):

- **凭据拒存与脱敏**:产物文本过凭据检测,命中则拒存、计入 `refused`。
- **sensitivity**:产物的 sensitivity = **来源条目的最大值**(只升不降);模型不能给产物降低 sensitivity。`sensitivity ≥ 1` 的来源只可能生成 `sensitivity ≥ 1` 的产物。
- **不可信来源进隔离区**:簇里任何一条来源是 `quarantined` 或来自不可信内容(邮件、网页),**整个簇的产物只进隔离区**(`status = quarantined`),不进入召回与 digest。更简单也更安全的做法是:**簇里有隔离区或不可信来源的条目就不参与整理**(推荐;见问题 8)。
- **审批**:`memory.write` 的审批与条件预授权规则不变。因为 sleep 是无人值守的,**sleep 的写入不使用条件预授权**,而是走专用的「系统整理」通道:**推荐方案:产物直接写入,但默认以较低置信度并标记 `origin = 'consolidated'`,Web 记忆页可一键撤销整个 `extract_run`**(沿用 `autoExtract` 的「已记住:… [撤销]」交互与「一键关闭」)。是否需要逐条审批由业主在问题 7 中决定。
- **digest 不改**:digest 继续按规则拼装,**不用 LLM 改写画像**(ADR 0007 第 5.10 节第 2 条),`consolidated` 条目按普通 `semantic` 条目参与规则,受 sensitivity 与渠道过滤约束。
- **生成日志**:每次真正调用了模型的 sleep 写一行 `memory_extract_runs`(`job = 'memory.sleep'`,`prompt_version` = 整理提示词 SHA-256 前 12 位,计数 `written` / `quarantined` / `refused`,错误码 `timeout` / `model_error` / `invalid_output`);不存正文、模型输出、错误信息。

### 6.3 上限(每次运行)

| 项                 | 默认上限                                         | 说明                                                         |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| LLM 调用次数       | **10**                                           | 与 ADR 0007 第 9 点一致;每个簇一次调用,不重试同一簇          |
| 每簇来源条数       | 12                                               | 超出的按相关度取前 12                                        |
| 每次运行新增条目   | 20                                               | 超出的簇留到下次                                             |
| 每次运行读取的候选 | 500                                              | 从最近更新且未整理过的里选,不全表扫描                        |
| 运行时额外内存     | **< 60 MiB**(目标;CI 测的是增量上限 **+30 MiB**) | 分批读取、聚类用现有向量(不另载模型)、不一次性把全部正文读入 |
| 单次运行最长时间   | 30 分钟                                          | 超时中止,已写入的保留(写入是逐条的)                          |
| 每日运行次数       | 1                                                | 防止手动连点;手动运行有 1 小时冷却                           |

整理过的来源条目打上「已被整理」标记(通过 `derived` 边的存在判断,不加列),下次不再重复选入,除非来源被更新。

### 6.4 与 2 GB 预算的关系

聚类用现有的向量检索(M2 的 embedding 索引),候选用分页查询,不在内存里建大矩阵;LLM 调用串行(共用 LLM 信号量);运行结束后释放。ADR 0018 的规则 3(运行后稳态回落 ≤ 60 MiB)适用于 sleep;PR 6 加一个合成数据(5k 条记忆)的运行用例(`pnpm perf:sleep`,参照 `scripts/perf/` 现有方式,假模型端点),测运行期间峰值与结束后回落。

### 6.5 不新增表、不改记忆 schema 的确认

`origin = 'consolidated'`、`ItemRel 'derived'`、`memory_extract_runs.job = 'memory.sleep'` 已在 0001 / 0012 预留。若实现中发现需要新状态(如 `proposed`),**先停下,写进 PR 描述,按迁移流程处理**,不擅自加列(见问题 7)。

### 6.6 评测(`pnpm eval` 记忆评测的扩展)

- **召回不退步**:整理前后,现有记忆评测集的召回率不下降、过时率不上升、错误率不上升(验收对照 ADR 0007 第 9 节 ①–⑧)。
- **注入**:簇中含恶意指令文本的条目(来源为邮件)→ 产物不生成或进隔离区;产物里出现凭据 → 拒存。
- **sensitivity 单调**:产物 sensitivity ≥ 所有来源;群聊 / digest 过滤用例不泄露 `sensitivity ≥ 1` 的整理产物。

## 9. 待业主决定的问题(每条先写推荐;不回复就按推荐做,例外见本节末尾)

1. **渠道推送的审批能否对「推给主人自己的微信」放宽?** 业主的规则是「发渠道消息一律走现有审批」,所以每次推送都要在微信里回复「确认 K7」,「每天 8 点摘要发微信」就变成「每天先收到一条确认请求」。推荐:**不放宽**,按规则做,并在文档里如实说明这个体验;摘要的审批消息里带内容预览,确认后即发。若以后想放宽,必须新增一个独立的 ADR 与审批类型(`external` 的「推给自己」子类),不在 M6。
2. **默认时区与系统任务时间。** 推荐:沿用 ADR 0023 的用户时区(未设置时取服务器系统时区),维护任务仍为 03:30、`sleep` 为 04:00,可在任务页修改。
3. **一次性任务过期后的默认策略。** 推荐:`once` 默认 `catchUp`(补跑一次),`cron` 默认 `skip`。理由:一次性提醒错过了应补;每天的任务补跑昨天的意义不大。
4. **全局并发默认值与每日 `agent_prompt` 上限。** 推荐:并发 2(LLM 密集型任务同一时刻最多 1 个),每日 `agent_prompt` 运行上限 50。2 GB 机器上更保守,可调。
5. **文件变化触发的范围。** 推荐:只监听已授权目录(`fs_roots`),最多 20 个目录、去抖 5 秒、不递归监听整个磁盘;不做「监听任意路径」。
6. **IM 里能不能创建任务?** 推荐:**不能直接生效**;微信里发的「每天 8 点……」只能生成草稿并回复「请到 Web 确认」。理由:确认卡片需要展示字段和警示,IM 里的纯文本确认太容易被误触;审批式确认留到以后。
7. **`memory.sleep` 的产物要不要逐条审批?** 推荐:**不逐条审批,但默认关闭、默认低置信度、整次运行可一键撤销、Web 可看生成日志**;理由:逐条审批会让它无法无人值守,而它只写 `semantic` 摘要且不改动来源条目。若业主要求逐条审批,则改为产物落在隔离区,由主人在记忆页接受——这需要新状态,走迁移流程(等待用户)。
8. **整理时是否排除隔离区与不可信来源的条目?** 推荐:**排除**(更简单也更安全,第 6.2 节),不做「只进隔离区」的复杂分支。
9. **Webhook 是否进 PR 4?** 推荐:进,但默认关闭,令牌只显示一次,64 KiB 上限、速率限制,文档注明公网暴露必须走反向代理 + HTTPS(ADR 0031)。若业主觉得入站接口风险过大,可以从 M6 里拿掉,只保留邮件与文件事件。
10. **任务运行记录的保留量。** 推荐:每任务最近 200 条、全局 5000 条,由每日维护清理。
11. **`tool_chain` 是否保留。** 推荐:保留但极简(第 2.2 节,无表达式、无分支);如果 PR 3 评审认为与「提示词交给 Agent」重叠太多,可降级为内部实现细节(只给系统任务用),不对用户开放。
12. **自然语言解析用哪个模型。** 推荐:用现有最便宜的 chat 配置档,不新增配置项;**最终模型组合仍由业主确认**,与 v1.0 发布的模型选择问题分开。

**需要业主明确同意才能做**(不会因为不回复而自动执行):合并(含数据库迁移的 PR 0016、0017 由业主亲自确认并合并)、改动数据目录或真实数据、发信、发微信、打 tag / 发 Release、推送镜像、里程碑范围变化。遇到迁移、发布或范围变化时,该项停下,在 PR 描述最上面写「等待用户」,转做下一项。
