# M11 方案 · 移动端(PWA 先行)

设计记录见 [ADR 0045](../adr/0045-mobile.md)。云容器没有真机:iOS Safari、Android Chrome、真实推送服务都要业主验证,PR 描述里会列成清单。

**先说结论**:开发计划写的前置条件(配对、增量同步、断点续传、推送抽象已在阶段一实现)核对后**不成立**,见 ADR 0045 背景一节。所以 M11 从补前置能力开始。

## 需要业主决定的问题(我的推荐在前)

1. **设备配对与令牌**(新的认证入口)。推荐「一次性配对码换设备令牌,refresh 每次轮换,重放即吊销设备,设备令牌不能创建设备或令牌」。替代方案:让手机直接用个人访问令牌(不需要新入口,但手机上要手输一长串令牌,也不能轮换)。
2. **增量同步的迁移**(新增变更日志表)。推荐批准;实现前我会再按迁移流程列出备份和回滚方式。
3. **Web Push 经浏览器厂商的推送服务**(新的出站目标,默认关闭)。推荐批准;通知只含通用文字和深链。替代方案:M11 不做推送,手机只在打开时看到待审批。
4. **自建端到端中继**。推荐放到 1.x,先用 Tailscale 等现成方案;如果你想在 M11 做,我先写独立的安全设计。
5. **原生客户端路线**(Tauri mobile 还是 Swift / Kotlin)。推荐 PWA 验证后再定,不在 M11 实现。
6. **局域网访问默认关闭**。推荐保持默认关闭,只在用户显式打开并看到风险说明后才监听非回环地址(桌面版)。

## 仅业主可做

iOS Safari 与 Android Chrome 的安装、推送、语音输入真机验证;真实家庭 / 办公网络下的局域网配对;Tailscale 等方案的实际连通性;(若批准推送)在真机上确认通知只含通用文字。
