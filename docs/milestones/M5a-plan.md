ADR 0022 · 渠道框架(要点,细节在 ADR 里定):

- **适配器接口**(`packages/channels`,AGPL):

  ```ts
  interface ChannelAdapter {
    kind: 'wecom' | 'wechat';
    start(ctx: ChannelContext): Promise<void>; // ctx.receive(inbound) 交给框架;ctx.log、ctx.secrets
    stop(): Promise<void>;
    send(target: ChannelTarget, message: OutboundMessage): Promise<void>;
    capabilities: { markdown: boolean; maxTextBytes: number; voiceIn: boolean };
  }
  type InboundMessage = {
    channelId: string;
    externalMessageId: string;
    externalUserId: string;
    chat: 'direct' | 'group';
    forwarded: boolean;
    text: string;
    receivedAt: string;
    voice?: { mediaType: string; fetch(): Promise<Uint8Array> } | { transcript: string };
  };
  ```

- **主人绑定**:Web「渠道」页生成 6 位配对码(10 分钟、一次有效、最多试 5 次);IM 里第一个发「绑定 123456」的账号成为这个渠道的主人。之后只有主人的私聊消息进入会话;其他人的消息、群聊消息默认**忽略**(不回复、不进模型),只在渠道状态里计数。可在 Web 解除绑定。
- **会话**:每个渠道绑定一个会话(标题「企业微信」「微信」);`/new` 开新会话;`/source` 回复源码地址(第 15.4 节);`/help` 列出指令。会话在 Web 里照常可见,两边看到同一份记录。
- **审批**:`approval-required` 推给主人一条消息「需要确认:<summary>。回复『确认 K7』或『拒绝 K7』」;短码每个待审批调用一个,随审批过期;只认主人账号的私聊回复;回复走现有审批接口的同一条路径(写同样的审计)。Web 上照常可以批准。
- **出站**:1.0 的渠道只回复主人,不提供「发给任意 IM 联系人」的工具;主动推送只有审批提醒、降级提醒(ADR 0017 第 5 节的开关)与渠道状态通知。
- **富文本降级**:回复的 Markdown 按渠道能力转换:企业微信自建应用用它支持的 markdown 子集(只在企业微信客户端显示,微信插件里会变成纯文本,所以默认发文本);微信只发纯文本。代码块保留原文、去掉围栏;链接写成「文字 (网址)」;超过单条上限时按段切成多条,每条带「(1/3)」。
- **不可信内容**:IM 里主人自己说的话是用户输入;转发的聊天记录、引用的他人消息、链接卡片的标题与摘要按不可信内容处理(打 `untrusted` 标记,置会话的 `untrustedContentSeen`),与邮件同一套规则。
- **记忆的敏感度**:群聊上下文(1.0 默认不处理群聊,但框架要预留)的召回与 digest 只取 `sensitivity` ≤ 1 的记忆。
- **可靠性**:入站按 `(channelId, externalMessageId)` 去重,保留 3 天;每个渠道每分钟最多处理 20 条主人消息,超出时回复一次「太快了」;同一会话正在运行时新消息排队,不并发起第二轮。
- **存储**(迁移 0014):`channels`(id、ownerId、kind、label、enabled、config_json,其中密钥只存 `env:` / `file:` 引用)、`channel_bindings`(渠道、外部用户 id、绑定时间)、`channel_inbox`(去重,3 天后清理)、`channel_pairings`(配对码的哈希与过期时间)。
- **API**:`GET/POST /api/v1/channels`、`GET/PATCH/DELETE /api/v1/channels/{id}`、`POST /api/v1/channels/{id}/pairing`、`DELETE /api/v1/channels/{id}/binding`、`GET /api/v1/channels/{id}/status`;企业微信回调 `GET/POST /api/v1/channels/{id}/wecom/callback`(**不需要登录**,只靠企业微信的签名;见安全清单);微信扫码 `POST /api/v1/channels/{id}/wechat/login` 返回二维码内容与轮询状态。
- **能力**:`GET /api/v1/meta` 的 `capabilities` 增加 `channels`。

ADR 0023 · 用户时区:

- `Settings.timeZone`:IANA 名称(如 `Asia/Shanghai`、`America/Los_Angeles`),用 `Intl.supportedValuesOf('timeZone')` 校验;省略时用服务器的时区,并在设置页提示「当前跟随服务器」。
- 三方时区不一致时一律**按用户设置的时区**:系统提示里的「今天」与当前时间、记忆维护的 03:30、邮件工具的日期、以后的定时任务(M6)。IM 对方的时区不参与(1.0 只和主人对话)。服务器时区只用于日志时间戳(日志统一写 UTC,`time` 字段已经是 ISO)。
- 改时区后,下一次维护按新时区排期;已排期的不补跑。

验收:两份 ADR 定稿;shared 中的新 schema 只新增,不改已有 schema;OpenAPI 检查通过。

## 3. 安全检查清单(每个 PR 都要过)

- 渠道只认绑定的主人;非主人与群聊消息默认忽略,不进模型。
- IM 中的审批只认主人私聊里的短码,短码随审批过期,写和 Web 审批相同的审计。
- 转发、引用、链接卡片按不可信内容处理;对外发送一律需审批。
- (企业微信推迟,以后适用)企业微信回调不需要登录,所以**每个请求都先验签再解密**,签名错误返回 403,不解析正文;时间戳超过 5 分钟拒绝;正文大小上限 64 KiB。
- 密钥统一放在 `secrets.yaml`(或环境变量),数据库只存 `env:` / `file:` 引用;服务器写 `secrets.yaml` 时先备份、只改目标键、解析失败不写;`access_token`、iLink 令牌、消息正文不进日志;日志只记渠道 id、消息类型与长度。
- 新接口都需要登录(回调除外),按 `ownerId` 取数据;越权用例必须有。
- 不引入遥测、不引入 copyleft 依赖;企业微信的加解密只用 `node:crypto`;新增依赖先测内存(ADR 0018)。
- 净室:只依据企业微信与 iLink 的公开文档、业主提供的资料和本方案;不复制第三方项目的代码。

## 5. 待业主决定

> **业主答复(2026-11-11,#17 评论)**:
>
> - 问题 1:企业微信整体推迟(不只是群机器人),M5a 先做渠道框架与微信 iLink,排期另定。
> - 问题 2:业主没有自己的桥接项目,开发计划里「业主已有的桥接项目」指的是之前看过的第三方公开项目(开发计划已更正)。参考 `@tencent-weixin/openclaw-weixin`(MIT,优先)与 `gfydfhcf/wechat-ilink-muse-bridge`(MIT),按净室规则只读 README 和公开协议说明,不读、不复制源代码;不够时列出缺少的细节等业主决定。PR 7 在 PR 2–5 合并后开始。
> - 问题 5:同意。iLink 令牌写入 `secrets.yaml`(权限 600);**所有密钥统一放在 `secrets.yaml`**(模型密钥、iLink 令牌、以后各渠道的密钥),M5b 加密时整体加密这个文件。写入时先备份、只改目标键、解析失败报错且不写入,要有测试。
> - 问题 3:随企业微信推迟。问题 4、6:没有另行答复,按建议做。

1. **企业微信用自建应用还是群机器人?** 群机器人的 webhook 只能发、不能收;能收消息的「智能机器人」接口和自建应用不同。**建议:1.0 只做自建应用**(一对一收发,能完成审批);群机器人以后需要往群里推送时再加。不回复就按建议做。
2. **微信 iLink / ClawBot 的协议资料从哪里来?** 开发计划说参考业主已有的 wechat-ilink 桥接项目,但它不在 `D:\Projects` 下已连接的文件夹里。**需要业主提供**:桥接项目的位置(或协议说明:扫码、长轮询、发消息的接口与字段),以及它的许可证(如果是业主自己写的,可以直接参考;如果来自第三方,按净室规则只读协议说明,不看代码)。PR 7 在拿到资料前不开始。
3. **企业微信回调需要公网可达的 HTTPS 地址**,而 TOTP 与密钥加密在 M5b 才做(开发计划要求公网暴露前完成)。**建议**:M5a 的文档只推荐用反向代理**只暴露回调路径** `/api/v1/channels/*/wecom/callback`,其他路径仍只在内网或 127.0.0.1;回调本身靠签名保护。另外,新建的企业微信自建应用要求配置**企业可信 IP**,回调域名要与企业主体备案一致,这两项需要业主在企业微信后台准备。不回复就按建议写文档。
4. **IM 里的语音消息怎么处理?** 企业微信语音是 AMR,微信语音是 SILK,M4 的转写接口不认这两种格式;解码要加依赖(多数 SILK 解码器的许可证需要核实)。**建议:M5a 只用平台自带的语音转文字结果**(有就用,没有就回复「暂时只能看文字,请发文字消息」),不加解码依赖;IM 回复语音推迟到 1.0 之后。M4 自检里写的「IM 渠道的语音 → M5a」改为按此执行。不回复就按建议做。
5. **iLink 扫码后拿到的令牌存在哪里?** 它是运行时产生的,不能像 API Key 那样只存 `env:` 引用;密钥加密存储在 M5b。**建议:写进数据目录的 `secrets.yaml`**(已有的 `file:` 机制,文件权限 600,Windows 上只给当前用户),M5b 做加密存储时一并迁移。这一条会改动数据目录,**需要业主明确同意**。
6. **非主人的消息是否回一句「这是私人助手」?** **建议:不回**(默认忽略,只计数),回复会暴露这是一个机器人,也会被用来探测。不回复就按建议做。
