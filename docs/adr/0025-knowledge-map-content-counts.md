# ADR 0025 · 知识地图显示内容条数

- 状态:已采纳(随知识地图计数修正一并落地)
- 日期:2026-11-11
- 相关:ADR 0012(条目计数)、ADR 0007 第 5.2 节(记忆导航树)、ADR 0016(邮件条目)

## 背景

知识地图括号里的数字用的是 `descendant_count`。它统计全部未删除后代,包括分类节点(记忆的域、类型、历史版本,邮件的账户、文件夹、会话串)。展开之后看到的是内容(记忆、邮件、会话、文件),两边对不上。同一封邮件如果同时在收件箱和已发送,条目树原先只挂在其中一个文件夹下,另一边是 0。

`descendant_count` 仍是移动和软删除时的子树大小,属性测试用它和递归计算对照。改它的含义要动所有写路径,也要改已经写进 ADR 0012 的契约。

## 决定

1. `Item` 增加可选字段 `contentCount`(向后兼容)。服务器在读出条目时现算,不新增数据库列,也不做迁移。
2. 算法:沿 primary `contains` 边向下,数 `kind = 'content'` 的后代;`meta.hidden = true` 的节点(记忆的「历史版本」)及其下面的条目不计入。分类节点本身不计数。这样每一层的数字等于默认展开(不带 `includeHidden`)能看到的内容条数。
3. Web 知识地图的括号改显示 `contentCount`。每次展开都重新拉取这一层,新写入的记忆和邮件不用先点「立即同步」才出现。记忆提供者的 `sync` 会把丢掉父边或标题与正文不一致的记忆挂回去(任务类 `episodic/task`、`semantic/task` 仍按 ADR 0007 挂在「经历」或「事实」下,不另开「任务」分类)。
4. 邮件条目:一封邮件在每个所在文件夹各有一条 `mail.message`(`source_ref` 带文件夹 id),打开时仍用原来的 `messageId`。账户指纹带布局版本,已经同步过的账户下次同步会按新布局重写。`descendant_count` 的维护方式不变。

## 后果

- 旧客户端忽略 `contentCount` 即可。知识地图上的数字与展开结果一致,已发送里能看到同时在收件箱中的邮件。
- 内容很多时,列出子项会为每个条目再跑一次递归计数。个人规模(万级条目、一次最多 100 个子项)可以接受;若以后 `children` 变慢,再考虑缓存,那时候才需要迁移。
