# ADR 0029 · 知识地图浏览器、人物与 `/map`

- 状态:已采纳(M5b PR 3;实现分布在 PR 7、8、9)
- 日期:2026-11-13
- 相关:ADR 0003(条目索引)、ADR 0012(条目 API)、ADR 0016(邮件与审批警告)、ADR 0022(渠道)、ADR 0025(`contentCount`)、开发计划 4.1.1 与 6.2、M5b 方案第 5 节问题 6–8、10
- 净室:联系人识别只依据本 ADR 与方案,不参考第三方项目的代码。

## 背景

知识地图 1.0 是列表 / 树形浏览器(粒子球在 M10)。ADR 0012 明确把 `/items/{id}/related`、`POST /items/{id}/ask` 与 ETag 留到 M5。M5b 要补齐它们,加入「人物」分类,并让微信里能用 `/map` 下钻。全部是对现有 API 的**新增**,不改已有响应。

## 决定

### 1. 新增接口(shared:`packages/shared/src/items.ts`)

| 端点                                       | 说明                                                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `GET /items/{id}/related?cursor&limit&rel` | `ItemRelatedPage`:该条目的**非 primary** 边(出边与入边),每项 `{ item, rel, direction }`,游标分页                           |
| `POST /items/{id}/ask`                     | `ItemAskRequest { scope: 'item' \| 'subtree' }` → `ItemAskResponse { sessionId, prompt, untrustedContentSeen, truncated }` |

- 软删除的条目当作不存在(404);别人(别的 `ownerId`)的条目一律 404,不区分「不存在」。
- `related` 只返回主人自己的、未删除条目;`contains` 的 primary 边不出现(走 `children` / `ancestors`)。
- `ask` 与 `POST /mail/messages/{id}/ask` 同形:创建会话并返回**预填提示词**,客户端填入输入框,不自动发送。`scope: 'item'` 带条目标题与摘要;`'subtree'` 带子树的标题与摘要列表,总量与条数有上限(超出置 `truncated: true`)。
- **不可信内容**:条目标题、摘要、联系人显示名都来自外部文本。`ask` 创建的会话,只要被引用的条目或子树里含 `mail.*` 条目,就置会话 `untrustedContentSeen`(与现有「问 AI」邮件入口一致,这一事实在响应里如实回报)。提示词把这些文本包成 `UntrustedContent`,不渲染 HTML。
- 两个端点需要登录;`ask` 是写操作(创建会话),需要 CSRF;`related` 只读。
- OpenAPI 的路径声明随 PR 7(`related`)与 PR 8(`ask`)的路由一起加入,只增不改。

### 2. ETag 与条件请求

- 读接口(`roots`、`{id}`、`children`、`ancestors`、`counts`、`subtree`、`related`、`search`)增加**弱 ETag**(`W/"…"`):由响应体内容的哈希得出,不依赖新数据库列。
- 请求带匹配的 `If-None-Match` 时返回 `304`,无响应体。无 `If-None-Match` 的请求与现在的响应完全一致(只多一个 `ETag` 头)。
- `content`(正文)、`changes`、`sync` 不加 ETag。

### 3. `characters` 提供者(PR 7)

- 提供者 id `characters`;「人物」是顶层类别 `type = 'characters.root'`,`kind = 'category'`;人物条目 `type = 'character'`,`kind = 'content'`,`source = 'characters'`。
- 每个人物**恰有一条 primary `contains` 边**挂在「人物」根下(树里能下钻),保持严格树与计数规则(ADR 0012 第 1 节:计数只沿 primary 边)。
- 人物到邮件用**非 primary** 的 `mentions` 边(出边;邮件的入边就是「也出现在…」)。**每人最多链接最近的 200 封邮件**,按邮件日期取;重新同步时重算该人物的边。非 primary 边不改变 `descendant_count`。
- 人物条目只含显示名、规范化地址(`source_ref` 为小写地址)、邮件计数与最近往来时间(放 `meta`);不读邮件正文,只取 From / To / Cc 的显示名与地址。
- 敏感度:`sensitivity > 1` 的记忆不混进人物条目;这一版人物只来自邮件(记忆里抽取人物不在 M5b)。

### 4. 联系人识别规则

候选地址只取自已同步邮件的 From / To / Cc,按**小写地址**去重。算作联系人的:

1. **主人发出过邮件的收件人**(To / Cc);
2. **来信不少于 2 封的发件人**。

排除:本机账户自己的地址;`noreply`、`no-reply`、`donotreply`、`do-not-reply`、`mailer-daemon`、`postmaster`、`notifications?` 等明显的系统发件地址(本地部分匹配,大小写不敏感);**带 `List-Id` 头的群发邮件**产生的地址。显示名取最近一次邮件里出现的非空显示名(没有则用地址的本地部分),长度截断到 200 字符,控制字符与双向控制符去掉。不做人物合并与手动编辑(推迟)。阈值是启发式,调整不涉及数据迁移。预计不需要迁移(`items`、`item_edges` 已有 `rel` 与 `primary_edge`);如实现中发现必须加索引或表,停下来在 PR 里说明。

### 5. `/map`(PR 9)

IM 里的知识地图下钻。状态只在渠道运行器的**内存**中(不入库),随进程重启消失。

- `/map` 列出顶层类别与编号;只含标题与计数(`contentCount`)。
- **应答窗口 5 分钟**:最近一次 `/map` 回复后 5 分钟内,**整条消息只有数字、`0` 或「返回」**才算应答;其余消息按普通聊天处理。**带引用(`quoted` 非空)的消息不算应答。** 窗口过期后的数字按普通聊天。
- 数字:进入对应条目的子项;`0` 或「返回」:回上一层;已在顶层时提示再发 `/map`;再发 `/map` 回到顶层。
- **每页最多 9 项**,编号 1–9。翻页用文字应答:**整条消息只有「下一页」或「上一页」**同样算应答(同一窗口、同一限制),数字不用于翻页。页末提示「回复『下一页』翻页」。每次有效应答都重置 5 分钟窗口。
- **叶子节点不发正文**:只给标题、类型与截断的摘要(摘要最多 120 字符),并提示「在 Web 打开」。从 IM 打开正文与发起「问 AI」不做(推迟)。
- **`/map` 的回复不写入会话**:不进模型上下文,不触发 `untrustedContentSeen`,也不记入记忆。
- 条目标题(邮件主题等)是不可信文本:作为纯文本输出,折叠换行,截断到 60 字符,并且出站文本永远不被当指令解析(标题里写「确认 K7」不产生审批)。
- 仅主人私聊:非主人、群聊的 `/map` 与数字沿用「忽略类」处理(不回复、计入每分钟 120 条上限);`/map` 与 `/new`、`/help` 一样计入主人限流。只读主人(`ownerId`)的条目。
- 单条回复的字数沿用渠道的切段与降级规则,超长时截断列表而不是分多条。

## 后果

- 旧客户端不受影响(新增端点与新增 ETag 头)。
- 人物边的数量受 200/人 限制;1 万封邮件下的内存与耗时在 PR 7 按 ADR 0018 实测后写进 PR(必要时调整该上限)。
- `/map` 的应答规则偏保守,代价是主人手误或翻页需要多发一条消息。

## 实现 PR 的测试清单

PR 7(`characters` 与 `related`):

- 地址规范化与去重;联系人规则(发出过邮件的收件人、来信 ≥ 2 封、排除系统发件地址、排除带 `List-Id`、排除本机地址);显示名取最近一次并清洗控制字符。
- 每个人物恰有一条 primary 边;非 primary 边不改变 `descendant_count`(沿用 `items-counts.test.ts` 的对照);超过 200 封只链接最近的;软删邮件后边与计数一致。
- `related`:入边与出边、`rel` 过滤、分页;**越权**:别的 `ownerId` 的条目 404、已删除条目 404、未登录 401。
- 1 万封合成邮件下的空闲 RSS 与同步耗时(ADR 0018),数字写进 PR。

PR 8(`ask`、ETag、浏览器):

- `ask` 的上下文组装(`item` / `subtree`、上限与 `truncated`);含邮件的条目置 `untrustedContentSeen`,不含邮件的不置;提示词里的条目文本被包成不可信内容(注入用例:标题里写「忽略以上指令」);**越权**:别人的条目 404、未登录 401、缺 CSRF 403、已删除条目 404。
- ETag:相同内容返回 304;内容变化后返回 200 与新 ETag;无 `If-None-Match` 的响应与旧版逐字相同(回归);已有 OpenAPI 响应不变。
- 分页合并不重复不丢;虚拟窗口范围计算;面包屑切换;Playwright 冒烟:从「邮件」「小说」「人物」各下钻到最深条目并打开,含手机宽度。

PR 9(`/map`):

- 非主人、群聊的 `/map` 与数字被忽略(忽略类,计入 120 条上限);**带引用的数字不当应答**;窗口 5 分钟过期后的数字当普通聊天;含其他文字的消息(如「2 好的」)当普通聊天。
- 叶子不发正文;每页最多 9 项,「下一页」「上一页」行为;`0` / 「返回」/ 再发 `/map`。
- 标题里写着「确认 K7」之类的文字不产生审批;`/map` 回复不写入会话(会话消息数不变、`untrustedContentSeen` 不变)。
- `/map` 与 `/new`、`/help` 同样计入主人限流;别的 `ownerId` 的条目不出现。
