# ADR 0023 · 用户时区:「今天」与定时任务按用户设置的时区

- 状态:提议(M5a PR 3 `docs/m5a-contracts`);实现见 M5a PR 4 `feat/user-timezone`
- 日期:2026-11-10(America/Los_Angeles)
- 相关:开发计划第 8 节 M5a(「用户时区设置与 ADR,默认按用户时区」);ADR 0007 第 5.7 节(记忆维护 03:30)、ADR 0014(嵌入每日上限)、ADR 0016(邮件工具的 `today`)、ADR 0022(渠道)

## 背景

现在所有「按天」的逻辑用的是服务器的时间,而且不一致:

- 记忆维护由 croner 在**服务器本地时间** 03:30 运行,但「今天已经跑过」的日期键用的是 **UTC** 日期(`toISOString().slice(0, 10)`)。
- 嵌入每日上限(5,000 次)与自动抽取每日上限的日期键也是 UTC。
- 邮件工具的 `today` 与 `time.now` 工具的默认时区取服务器进程的时区(`Intl.DateTimeFormat().resolvedOptions().timeZone`),Docker 里通常是 UTC。

自托管时服务器、主人、IM 对方可能在三个时区:例如容器跑在 UTC,主人在上海。主人说「今天的邮件」是上海的今天;03:30 的维护应该在主人睡觉时跑,而不是上海的上午 11:30。

## 1. 决定

1. 新增设置 `Settings.timeZone`:IANA 区域名(如 `Asia/Shanghai`、`America/Los_Angeles`)或 `UTC`;`null` / 省略表示**跟随服务器**,设置页显示「当前跟随服务器(<服务器时区>)」。
2. 凡是对用户有意义的「今天」「现在」「每天几点」,一律按**用户时区**(设置了用设置,没设置用服务器时区)。
3. 服务器时区只剩一个用途:没设置用户时区时的默认值。日志时间戳保持 UTC ISO(`time` 字段,已是现状),不随用户时区变化。
4. IM 对方的时区不参与(1.0 只和主人对话,ADR 0022)。

## 2. 合法的时区名

- 只接受 `Area/Location` 形式的 IANA 名(最多三段,如 `America/Argentina/Buenos_Aires`、`Etc/GMT+8`)与 `UTC`;拒绝 `+08:00` 这类固定偏移、`CST` 这类缩写(含义不唯一,也不随夏令时变化)。
- 校验用 `new Intl.DateTimeFormat('en-US', { timeZone })` 能否构造,而不是只查 `Intl.supportedValuesOf('timeZone')`:后者在 Node 24 里**不含 `UTC`**,且只列出 ICU 的规范名(例如有 `Asia/Calcutta` 没有 `Asia/Kolkata`)。别名照样接受,原样保存用户选的名字。
- 契约:`packages/shared/src/time-zone.ts` 的 `TimeZoneName` 与 `isSupportedTimeZone`(本 PR 新增)。

## 3. 契约

本 PR 只新增 schema,不改动已有的 `Settings`,OpenAPI 不变。PR 4 再做以下**只增**的修改:

```ts
// Settings 中(GET / PUT /api/v1/settings)
/** 用户时区;null 表示跟随服务器(ADR 0023)。自 M5a PR 4 起提供,旧服务器不返回。 */
timeZone: TimeZoneName.nullable().optional(),
```

- `PUT /api/v1/settings` 传 `timeZone: null` 恢复跟随服务器;传不合法的名字返回 400(`issues` 指向 `timeZone`)。
- 新增 `GET /api/v1/settings/time-zones` → `TimeZoneInfo { serverTimeZone, supported }`:`supported` 是 `Intl.supportedValuesOf('timeZone')` 加上 `UTC`,供设置页做可搜索的下拉框;需要登录(服务器时区会透露部署位置,不放进不需要登录的 `/meta`)。
- 客户端遇到老服务器(没有 `timeZone` 字段、或 `time-zones` 返回 404)时不显示这个设置。

## 4. 哪些地方改为按用户时区(PR 4)

| 位置                           | 现在           | 改为                                                                   |
| ------------------------------ | -------------- | ---------------------------------------------------------------------- |
| 记忆维护的 03:30               | 服务器本地时间 | croner 的 `timezone` 选项用用户时区                                    |
| 维护「今天已跑过」的日期键     | UTC 日期       | 用户时区的日期                                                         |
| 嵌入每日上限、自动抽取每日上限 | UTC 日期       | 用户时区的日期                                                         |
| 邮件工具的 `today`             | 服务器进程时区 | 用户时区                                                               |
| `time.now` 工具的默认时区      | 服务器进程时区 | 用户时区(调用时显式传 `timezone` 的照旧)                               |
| 系统提示                       | 没有当前时间   | 增加一行「当前时间:2026-11-11 15:30(Asia/Shanghai,星期三)」,精确到分钟 |
| 定时任务(M6)                   | —              | 按用户时区排期                                                         |
| 日志 `time`                    | UTC ISO        | 不变                                                                   |

- 系统提示里的时间只到分钟、不带秒,少一些无意义的变化;星期的写法跟随 `locale`。
- 数据库里存的时间戳一律保持 UTC ISO,只在「算日期」和「显示」时换算。

## 5. 改时区的时机

- 保存新时区后,维护任务立即按新时区重新排期(停掉旧的 croner 任务、建新的);**已错过的不补跑,也不为了「今天」再跑一次**:日期键换算后若这一天已标记完成,就跳过。
- 每日上限的日期键换到新时区后可能出现「同一天」被算两次或少算的情况(例如从 UTC 改到 UTC+8,某一天的配额会提前重置一次)。这是一次性的,接受,不做迁移。
- 夏令时:要求切换日既不漏跑也不重跑。重复的那天由日期键保证只跑一次;03:30 被跳过的情况 croner 的行为在 PR 4 用 `America/Los_Angeles` 的切换日写单测确认,若会漏跑,就在当天第一次有效的整点补一次(仍受日期键约束)。(注:美国的切换在凌晨 2 点,03:30 本身不会落在被跳过或重复的时段;其他地区的切换时间不同,所以仍要测。)

## 6. 测试(PR 4)

- 跨日:`now = 2026-11-10T17:00:00Z`,用户时区 `Asia/Shanghai`(当地已是 11 日 01:00)时邮件工具的 `today` 是 11 日;服务器时区为 UTC 时不受影响。
- 维护:改时区后排期的下一次运行时间等于新时区的 03:30;同一天不跑两次。
- 校验:`UTC`、别名(`Asia/Calcutta`)接受;`+08:00`、`CST`、不存在的名字拒绝(本 PR 的 shared 单测已覆盖 schema 部分)。
- 界面:设置页「通用」的时区选择截图(跟随服务器 / 已选择两种状态)。

## 后果

- 「今天」「每天 03:30」在主人眼里终于是同一个意思,不再随部署方式(Docker 默认 UTC)变化。
- 多了一个设置项和一次重新排期的逻辑;多用户(2.0)时 `timeZone` 已经是按用户的设置,维护任务需要按用户分别排期,届时再修订第 4 节。
