# ADR 0018 · 服务端内存预算:从固定 120 MiB 门禁改为上限 + 防退化

- 状态:已实施(M3.x,业主 2026-11-10 决定方向;规则 1–4 由 M3.x PR 3 落到 CI,规则 5 由 M5a PR 8 落到 CI)
- 日期:2026-11-10
- 相关:开发计划第 11 节(性能)、第 12 节(资源预算)、M3.x、M5a、M5c;ADR 0013(MCP 子进程)、ADR 0014(sqlite-vec 按需加载)、ADR 0016 第 11 节(邮件同步在子进程中)
- 替代:M0 起 CI `docker image` 任务中固定的「空闲 RSS < 120 MiB」门禁

## 背景

从 M0 起,CI 用一个固定数字卡住镜像空闲内存:`test "$RSS_KB" -lt $((120 * 1024))`。到 M3 结束,实测是 110–111 MiB(main 最近 6 次 CI),离门禁只剩约 9 MiB。M5 还要加两个 IM 渠道,M4 要加语音,固定数字很快会逼着每个 PR 去争那几 MiB,或者干脆把门禁调高,失去意义。

另一方面,固定门禁只看「刚启动 10 秒」这一个点,看不到真正的问题:业主侧助手的合成测试(测的是测试脚本的父进程,不是完整产品或容器)发现,1 万封邮件同步后主进程 RSS 从 91.7 MiB 涨到 161.8 MiB,同步结束后也不回落;M3.x PR 2 用构建好的服务器复现,同步后停在约 265 MiB。门禁对这种情况完全没有反应。

业主 2026-11-10 的决定:空闲上限 250 MiB(不配置渠道时);每个渠道另定增量;长时间运行和大量同步后内存要能回落;CI 与上一个版本对比,涨幅超过 20% 就报警;桌面端和手机端以后单独定预算。本 ADR 把这些落成可执行的规则;其中「20% 就报警」已由第 2 节取代:涨幅 > 10% 报警,> 20% 失败。

## 1. 范围

- 只管**服务端 Docker 镜像**(linux/amd64,CI 的 `ubuntu-latest`)的**主进程**(容器内 PID 1)。
- 子进程(邮件同步、MCP 服务器、文档解析 worker)不计入空闲内存;但它们结束后,主进程的内存要回到正常水平(第 4 节)。
- 桌面端(M10,含 sidecar 与 WebView)和手机端(M11)单独定预算,不用本 ADR 的数字。
- 对话中的峰值 < 400 MiB 不变,仍在发布前测量(开发计划第 11 节)。

## 2. 规则

| #   | 指标                   | 规则                                                  | 不满足时                     |
| --- | ---------------------- | ----------------------------------------------------- | ---------------------------- |
| 1   | 空闲 RSS(不配置渠道)   | 启动后 10 秒测量,≤ 250 MiB                            | **CI 失败**                  |
| 2   | 空闲 RSS 相对基线      | 启动后 10 秒测量,涨幅 ≤ 10%                           | 通过                         |
|     |                        | 涨幅 > 10% 且 ≤ 20%                                   | **CI 报警**(注释,不阻塞合并) |
|     |                        | 涨幅 > 20%                                            | **CI 失败**                  |
| 3   | 负载后回落(第 4 节)    | 同一进程、每次运行:空闲 60 秒后 − 负载前空闲 ≤ 60 MiB | **CI 失败**                  |
| 4   | 不持续上涨(第 4 节)    | 同一负载连跑 3 次,第 3 次后比第 2 次后多 ≤ 5 MiB      | **CI 失败**                  |
| 5   | 每个渠道的增量(M5a 起) | ≤ 该渠道的增量上限(第 5 节表格)                       | **CI 失败**                  |

**为什么 20% 是失败而不只是报警**:只报警的检查在 CI 里很快就没人看了;而 20% 已经留了足够的空间(以现在的基线算约 22 MiB),超过它说明有一处明显的新开销,值得在 PR 里写明理由。10%–20% 之间只报警,让小的、合理的增长不必每次都改基线。

**通过的方法**:涨幅超过 20% 而又确有必要时,在同一个 PR 里更新基线文件(第 3 节)并在 PR 描述里写明原因;基线改动跟代码一起被审查。绝对上限 250 MiB 不能这样绕过,要改只能修改本 ADR。

## 3. 基线

- **基线文件** `.github/memory-baseline.json`:`{ "idleRssMiB": 111, "commit": "<sha>", "measuredAt": "<ISO 日期>", "note": "..." }`。初值取 M3 结束后 main 的 CI 实测(110–111 MiB,取 111)。
- **为什么不在每个 PR 里现场测 main**:要多构建一次镜像(CI 时间翻倍),而且还没有发布版本可比。业主说的「上一个版本」在 v1.0 之前按基线文件理解。
- **何时更新基线**:① 每次发布(打 tag,M5c 起)时改为该版本的实测值;② 某个 PR 有理由地增加了内存(第 2 节);③ 某个 PR 明显减少了内存时,可以顺手调低,让以后的检查更敏感。
- 基线只会被人改,CI 不自动写回。

## 4. 回落与不持续上涨

- **测法**:先记一次空闲 RSS,然后跑合成负载(M3.x PR 2 的「1 万封邮件同步」:本地假 IMAP 服务器 + 1 万封合成邮件,不连外网、不用真实账户),负载结束后空闲 60 秒再测。连跑 3 次。实现:`.github/workflows/memory-load.yml` 运行 `CHECK=1 pnpm perf:mail-sync`,在 runner 上直接运行构建好的服务器,Node 参数取自 `docker/Dockerfile` 的 `NODE_OPTIONS`;不放进容器,是因为假 IMAP 服务器与自签证书要从容器外连进去,复杂得多,而测的是同一个主进程、同一组参数。规则 1、2 仍在 `ci.yml` 的 docker 任务中对容器测(`scripts/perf/idle-budget.mjs`)。
- **为什么等 60 秒**:V8 的 GC 与 glibc 归还内存都不是立刻发生的;60 秒内回不来的,基本就是泄漏或缓存没上限。
- **采样**:每个测量点取 3 次采样(间隔 5 秒)的中位数,消除约 1 MiB 的抖动。
- 负载如果超过 3 分钟,改为只在 push 到 main 与手动触发(`workflow_dispatch`)时跑,PR 上只跑规则 1、2。实测(M3.x PR 2,本机 Linux):1 万封一次同步约 100 秒,3 次加上每次 60 秒空闲约 8 分钟,所以按这一条处理。
- **规则 3 为什么用同一进程的绝对增量**:负载之后有一部分内存是有上限的缓存,不会再还回去,也不该算泄漏:V8 老生代按负载调大后的大小、SQLite 页缓存(4 MiB)、malloc 留下的空闲块。M3.x PR 2(#48)实测:修复后负载前空闲 106.9 MiB,3 次同步后 60 秒分别是 140.8 / 145.0 / 145.3 MiB,增量 34–38 MiB;修复前 108.3 → 264.7 / 266.0 / 266.1 MiB,增量约 156–158 MiB(业主侧助手机器上约 168 MiB)。60 MiB 给修复后的版本留了约 20 MiB 余量,又能抓到修复前那种问题。不用「基线 × 倍数」:基线文件来自另一次测量(CI 容器),和负载前空闲口径不同;而且调低基线会连带收紧回落线。
- **规则 4 为什么比第 2、3 次**:第 1 次负载包含缓存填满等一次性的增长,第 2、3 次之间才看得出是否还在涨。实测修复后第 2→3 次 +0.3 MiB,修复前 +0.1 MiB:原来的问题是一次涨上去不回落,由规则 3 负责,规则 4 只防「每跑一次都多一点」的泄漏。
- **以后考虑按时间的 soak 测试**:例如服务器空转或渠道长轮询运行数小时,定时采样 RSS,看是否随时间上涨。负载与时长在 M5a 渠道接入时定,先在 `workflow_dispatch` 或每晚运行。
- 以后的负载(例如 M5a 的渠道长轮询、M6 的定时任务)按同样的方法加入。

## 5. 每个渠道的增量(M5a)

- **测法**(`scripts/perf/channel-rss.mjs`,`pnpm perf:channel`):CI 里起一个假的微信 iLink 服务器(`fake-ilink.mjs`:扫码立刻确认、`getupdates` 长轮询、`sendmessage` 只计数,不连外网)和构建好的服务器。服务器代码不改:`ilink-redirect.mjs` 以 `node --import` 预加载,把发往 iLink 默认地址的请求改到本地假端点。先测不配渠道的空闲 RSS(启动后 10 秒,3 次采样取中位数),再走真实流程配好渠道(建渠道、扫码、配对、启用、主人发「绑定」),空闲 60 秒后再测;**两者之差就是该渠道的增量**。企业微信已推迟,不测。
- **规则 3、4 对渠道的做法**:主人发 100 条普通文字消息,每条都走完整的一轮对话(收消息、去重、限流、入队、`runs.start`、模型流式输出、写消息与会话、回复文本)。模型是本地假的 OpenAI 兼容端点(`fake-openai.mjs`,`/v1/chat/completions`,流式返回几段固定文字),通过真实的模型配置档接入(密钥用 `env:` 引用),不连外网。脚本数每次运行的模型调用次数,少于消息数即失败。等回复收齐后空闲 60 秒再测,连跑 4 次。不用 `/help`:它在指令分支直接返回,不进入对话路径,测不到渠道最可能泄漏的地方(M5a 验收以对话路径为准)。规则 3 的基准是「配置渠道后的空闲」;规则 4 比较最后两次。主人消息每分钟最多 20 条(ADR 0022 第 4 节),所以每 3.4 秒一条,单次约 6 分钟,整个任务约 27 分钟,只在 push 到 main 与手动触发时运行(`memory-load.yml` 的 `channel-wechat` 任务)。
- **为什么规则 4 比最后两次而不是第 2、3 次**:渠道的堆在头几次负载里会一次性长一档,不是持续上涨。实测 3×100:117 / 119 / 126 MiB(第 3 次比第 2 次多 7.1 MiB);4×100:121.4 / 122.9 / 127.6 / 128.3 MiB(最后一次 +0.7);6×40:112.5 / 114.8 / 117.1 / 117.5 / 117.9 / 118.4 MiB,到第 4 次起每次不到 0.5 MiB。第 2、3 次相比会因一次性的台阶误报,最后两次才看得出是否还在涨。
- **上限 = 实测增量 × 1.5,向上取整到 5 MiB**。上限放在 `.github/memory-baseline.json` 的 `channelIncrementMiB`(CI 读取这个文件),下表是同一数字的说明;改上限要同时改两处并在 PR 里写明原因。

| 渠道     | 实测增量(Linux,Node 24,5 次测量)     | 上限  |
| -------- | ------------------------------------ | ----- |
| 微信     | +1.8 / +1.9 / +2.1 / +2.9 / +3.2 MiB | 5 MiB |
| 企业微信 | 推迟                                 | 待定  |

- **本机复测(未通过,待 CI 数据)**:同一台 Linux 机器(Node 24)上,PR 原来的脚本与本次改动后的脚本都测得增量约 +13.3 至 +13.8 MiB,远高于上表的 +1.8 至 +3.2 MiB。原脚本在本机不带模型配置档时也是 +13.8,所以不是模型配置档造成的。原因未查清,在 CI runner 上的数字出来之前不改上限。
- 配置了渠道时,规则 2(相对基线的涨幅)按「基线 + 已配置渠道的增量上限之和」计算。ci.yml 的 docker 任务不配渠道,所以这一条目前由使用者理解;渠道增量本身由规则 5 单独卡住。

## 6. 实施顺序

1. 本 ADR 合并(只改文档)。
2. M3.x PR 2:合成 1 万封同步压测,查清并修复 91.7 → 161.8 MiB 不回落的问题;在本 ADR 第 4 节补上负载用时。
3. M3.x PR 3(CI,已完成):新增 `.github/memory-baseline.json`、`scripts/perf/idle-budget.mjs` 与 `memory-load.yml`,实现规则 1–4,同一个 PR 里删除了 `ci.yml` 中固定的 120 MiB 门禁。
4. M5a PR 8(已完成):规则 5 与渠道负载。

## 7. 运行参数与不变的部分

- **新生代上限 `--max-semi-space-size=8`(M3.x,#48)**:默认的半空间上限随堆上限变大,大批量写入后新生代涨到约 128 MiB,空闲时也不归还。Docker 镜像的 `NODE_OPTIONS`、`apps/server` 的 `pnpm dev` 与 `start` 命令行都带这个参数(Windows 下同样生效)。实测 4 MiB 连跑 3 次内存持续上涨(业主侧助手机器 133 → 139 → 143 MiB),吞吐没有差别,所以用 8。同一台 Linux 机器上对比 8 与默认(各 3 次、做两遍,1 万封):8 为每次 104–110 秒,默认为 102–107 秒,差约 2%,在抖动范围内;两者每次之间都只慢 0–6 秒。
- **SQLite 页缓存 4 MiB**(`PRAGMA cache_size = -4000`,ADR 0005 第 2 节):better-sqlite3 默认 16 MiB,填满后一直占着。
- `--max-old-space-size=384`、文件索引走 worker 并限并发(开发计划第 12 节)不变。
- 「按需加载」的做法不变:可选功能(sqlite-vec、邮件、MCP、`ws`)只在配置后才加载,没配置时不占空闲内存。新依赖仍要先测量再引入。
- 「Memory breakdown (informational)」步骤保留,继续逐个模块列出 import 后的 RSS,方便定位涨幅来自哪里。

## 8. 后果

- 新功能有了空间(250 MiB 上限、相对基线 20%),但每次明显增长都要在 PR 里留下理由。
- 能抓到「启动时正常、跑一阵就涨」这类问题,这是固定门禁看不到的。
- CI 时间增加:3 次采样约多 10 秒;负载测试在第 4 节规定的范围内。
- 基线文件要人维护,发布清单(M5c)里加一项「更新内存基线」。
