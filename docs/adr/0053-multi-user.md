# ADR 0053 · 多用户(2.0,M13 后段 4)

- 状态:提议(按 `docs/milestones/M13-plan.md`「后段顺序」第 4 项)
- 日期:2026-11-25
- 相关:开发计划第 9 节 M13「多用户(2.0 核心目标)」与第 16 节「1.0 仅单用户,表结构预留 `ownerId`」;ADR 0003(`ownerId`)、ADR 0005(存储与迁移)、ADR 0022(渠道绑定与审批,第 9 节 secrets.yaml)、ADR 0051(ownerId 覆盖审计)、ADR 0052(QQ 渠道)
- 范围:只写设计和分 PR 计划,本 PR 不改代码。实现在 2.0,本 ADR 被业主确认之后按第 12 节分 PR 做。
- 语言:中文;代码标识符、表名和文件名保留英文。

## 0. 背景

1.0 只允许一个主人账户:`owners` 表上的触发器 `trg_owners_single` 拒绝第二行。但从 M1 起每张「属于某个人」的表都带 `owner_id`,ADR 0051 审计过:55 张表里 38 张带 `owner_id`,其余 17 张是子表、全局状态或 `owners` 本身;271 个仓储方法里 183 个按 `ownerId` 过滤,另外 88 个登记了理由;61 条带路径参数的路由用别人的 id 都拿不到数据。`pnpm check:owner-scope` 与 `owner-scope.test.ts` 在 CI 里守着这条线。

所以多用户的数据隔离大部分已经有了。剩下的难点不在数据库,而在**整个安装共用的东西**:服务器进程以同一个系统用户运行,授权文件夹、MCP 服务器、插件进程、编码项目的命令都直接作用在这台机器上;`secrets.yaml` 只有一份;嵌入模型状态是全局的。多用户的设计主要是回答「这些东西谁能用」。

目标场景是开发计划第 1.3 节的家庭和小团队:一个人装好、管理,给家人或同事各开一个账户,各自的对话、记忆、知识地图、邮箱和渠道互相看不到。

## 1. 目标与非目标

**目标**

1. 多个账户,各自登录,数据按 `ownerId` 完全隔离(会话、记忆、知识地图、邮箱、渠道绑定、任务、代理、设置、审批、预授权、设备与令牌)。
2. 两种角色:`admin`(管理员)与 `member`(成员)。会碰到宿主机的能力只有管理员能开。
3. 1.0 单用户数据无损升级:原来的主人变成管理员,数据一行不动。
4. `/api/v1` 只做向后兼容的增量修改;单用户安装升级后,现有客户端行为不变。

**非目标(2.0 不做)**

- 公开注册、SSO / OIDC / LDAP、组织和团队层级、用户组。
- 账户之间共享会话、记忆或知识地图条目。
- 按用户的系统级沙箱(不同系统用户运行、容器隔离)。
- 数据库行级安全或每个用户一个数据库文件(第 11 节说明原因)。
- 按用户计费或用量配额的报表(只做防止一个人占满资源的上限,第 8 节)。

## 2. 账户与角色

- 仍用 `owners` 表,一行就是一个账户;代码里继续叫 `ownerId`,不改名(改名会碰几乎所有文件,收益为零)。
- 新增列 `role TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('admin','member'))`、`disabled_at TEXT`、`display_name TEXT`。
- 迁移:删掉 `trg_owners_single`,已有的那一行设为 `admin`。至少保留一个未停用的管理员:新触发器拒绝把最后一个管理员降级、停用或删除。
- **建账户**:只有管理员能建。管理员生成一个**邀请码**(一次性、24 小时有效、只存哈希,和配对码同样的形状和重试上限),对方在登录页用邀请码设置自己的用户名和密码。不做管理员直接替别人设密码(避免管理员知道成员的密码)。
- **重置密码**:管理员只能给成员生成一个新的邀请码式「重置码」,成员用它设新密码;重置后该成员的登录会话、访问令牌和设备刷新令牌全部作废,TOTP 保留。
- **停用**:停用的账户不能登录,已有会话和令牌立即失效;它的定时任务、邮件同步和渠道暂停(渠道状态显示「账户已停用」),数据保留。
- **删除**:删除前先做一次数据库备份(沿用 ADR 0005 的备份),然后靠 `ON DELETE CASCADE` 删掉这个账户的全部行;secrets.yaml 里它的密钥行(第 5 节的前缀)一并删除。需要输入该用户名确认。
- 管理员看不到成员的数据:没有「以某人身份查看」,管理接口只返回账户列表(用户名、显示名、角色、创建时间、最后登录时间、是否启用 TOTP、是否停用)。

## 3. 数据隔离

规则沿用 ADR 0051 第 2 节,不变:带 `owner_id` 的表按它过滤;别人的资源和不存在的资源对外一模一样。2.0 要补的是:

1. **越权测试换成真的两个账户**:`owner-scope.test.ts` 现在关掉外键往一个不存在的主人名下写数据;迁移之后改成真的建第二个账户,用正常的 API 造它的资源,再用第一个账户逐条扫。`check:owner-scope` 不变。
2. **事件与 WebSocket**:订阅只收到自己的事件。现在只有一个主人,事件总线没有按 `ownerId` 过滤的需要;实现时逐个事件源核对,加一条「两个账户各开一个 WebSocket,互相收不到」的测试。
3. **`system` 类方法**(ADR 0051 第 1 节的 26 个,后台任务对所有主人做的事):每行自带 `ownerId`,后续处理必须用这一行的 `ownerId`,不能用「当前主人」。实现时逐个复核,有问题的改成按主人分批。
4. **全文索引与向量**:`kb_chunks`、`mail_messages` 的 FTS 与 `embeddings` 查询都带 `owner_id` 条件(已有);补一条两个账户内容相同、检索只返回自己的测试。
5. **附件与数据目录里的文件**:按 `ownerId` 分子目录;读取时先查数据库行的 `ownerId`,不按文件名猜。

## 4. 安装级能力:只有管理员能开

服务器以一个系统用户运行。下面这些能力实际上是「让助手在这台机器上做事」,给成员开等于让成员拿到服务器的系统权限,所以 2.0 里**只有管理员能配置**:

| 能力                               | 管理员           | 成员                                                     |
| ---------------------------------- | ---------------- | -------------------------------------------------------- |
| 授权文件夹(`fs_roots`)、知识库目录 | 添加、删除       | 只能用管理员**分配给他**的文件夹(第 4.1 节),不能自己添加 |
| MCP 服务器(stdio 会起进程)         | 添加、删除       | 不可用                                                   |
| 插件(有 `entry` 的会起进程)        | 安装、卸载、更新 | 只能用管理员**开放给成员**的插件(第 4.2 节)              |
| 纯指令插件(只有 Skill,不起进程)    | 安装             | 同上                                                     |
| 编码项目与 `code.run`              | 登记项目和命令   | 不可用                                                   |
| 嵌入模型、监听地址、更新检查       | 设置             | 只读                                                     |
| 外连目标页                         | 看全部           | 看自己的(模型、邮箱、渠道)和管理员开放的插件             |

### 4.1 分配文件夹

管理员添加授权文件夹时可以选「给谁用」:自己,或某个成员。`fs_roots` 已有 `owner_id`,一行属于一个账户;同一个路径分给两个人就是两行。成员只能看到、读写分给自己的文件夹,写入仍然逐次审批。成员不能把文件夹再分给别人。

### 4.2 开放插件

插件进程整个安装只有一个(按包装一次),但调用记录、设置值、插件事件属于调用的那个账户。`plugins` 表的 `owner_id` 改为「安装的管理员」,新增 `shared_with_members INTEGER NOT NULL DEFAULT 0`。开放给成员的插件,成员的运行里能用它的工具;插件声明的 `secrets` 由管理员填写,成员看不到;插件的 `items` 权限写进调用者自己的条目。插件拿到的调用上下文带调用者的 `ownerId`,插件 SDK 文档写明插件不能跨账户缓存数据。

## 5. 密钥

`secrets.yaml`(或加密的 `secrets.yaml.enc`)整个安装只有一份,文件格式不变。

- **命名**:成员写入的密钥行用前缀 `U<ownerId>_`(例如 `U01JC…_OPENAI_API_KEY`)。管理员写入的不带前缀,和 1.0 一样,已有安装的密钥不改名。QQ 渠道的 `QQBOT_SECRET_<channelId>` 本来就按渠道 id 区分,不加前缀,但只有渠道的主人能写。
- **引用检查**:解析 `file:KEY` / `env:KEY` 时带上调用者的 `ownerId`:成员只能解析带自己前缀的键,以及管理员明确共享的模型配置档里的键(第 5.1 节);`env:` 引用只有管理员能用(环境变量是服务器的)。
- **写入**:沿用 ADR 0022 第 9 节:先备份、只改这一行。成员不能读回任何密钥的值(和现在一样,API 从不回显)。

### 5.1 共享模型配置档

家庭场景里通常是管理员付一个模型账号的费用,大家一起用。管理员可以把自己的模型配置档标为「共享给成员」:成员在选择模型时能看到它的名称和模型名,能用,但看不到地址里的凭据和密钥引用,也不能编辑或测试连接。成员也可以建自己的配置档(用自己的密钥)。

## 6. 鉴权

- 登录页已有用户名字段(`AuthForm.tsx`);多用户只是用户名不再固定。密码登录的失败限流现在只按来源地址计数(`FailureLimiter`,5 次 / 分钟),改为和第二因素一样按用户名与按来源地址分别计数,任一被锁定即拒绝;用户名不存在和密码错误回答一样。
- `POST /auth/setup` 只在一个账户都没有时可用(和现在一样);之后建账户只能走邀请码:`POST /auth/invite/accept`(`{ code, username, password }`)。
- TOTP、访问令牌、设备配对都按账户,已经是每行带 `owner_id`。
- 已有的 `GET /api/v1/auth/me`(`Me`:`id`、`username`、`createdAt`)增加可选字段 `role` 与 `displayName`。客户端靠它决定显示哪些管理入口;服务端每个管理路由自己再检查角色,不信客户端。
- 角色检查集中在一个中间件 `requireAdmin`;第 4 节的每个「只有管理员」的写操作都要有一条「成员调用回 403 `admin_required`」的测试,并加进一个和 `owner-scope.test.ts` 同样思路的扫描测试:OpenAPI 里标了 `x-fatcat-admin: true` 的路由,用成员身份逐条调用,全部 403 且数据不变。

## 7. 渠道

- 每个渠道属于一个账户,绑定一个外部账号(ADR 0022),这一点不变。成员可以自己建微信 / QQ 渠道(渠道连的是外部平台,不碰宿主机)。
- 同一个外部账号(同一个微信号)可以分别绑定两个账户的渠道,互不影响;这是两个不同的机器人账号,不会串。
- 群聊仍然一律忽略(ADR 0052 第 10 节)。「在一个群里服务多个账户」需要按发言人映射账户,2.0 不做。
- 渠道审批短码、待审批项都按渠道所属账户,不变。

## 8. 资源与公平

单机资源有限,一个人不能占满:

- 每个账户同时进行的运行数上限(默认 2,管理员可改;整个安装的上限另有设置)。超出时排队,不报错。
- 后台任务(定时任务、邮件同步、记忆抽取、嵌入队列)按账户轮转取活,不按插入顺序,避免一个账户的大邮箱把别人的任务饿死。
- 嵌入模型是整个安装共用的(`embed_state` 是全局状态,换嵌入模型要重建全部向量),只有管理员能换;成员看到「由管理员设置」。
- 磁盘:附件和知识库按账户统计用量,在账户列表里显示;2.0 不做硬配额。

## 9. API 与兼容

- 全部是增量修改:`/auth/me` 加可选字段,新增 `/admin/users`(列表、邀请、停用、启用、删除、重置码、改角色)、`/auth/invite/accept`;已有资源对象最多新增可选字段(例如模型配置档的 `shared`)。
- 已有路由对管理员的行为和 1.0 完全一样,所以单用户升级后现有客户端(Web、CLI、桌面、移动)不用改。成员调用「只有管理员」的路由回 403 `admin_required`,这是新错误码,写进 `ErrorCode`。
- OpenAPI 用 `x-fatcat-admin: true` 标注管理员路由;`oasdiff` 检查只应看到新增。

## 10. 迁移与回退

- 一个迁移:加 `owners` 的三列、删 `trg_owners_single`、加「最后一个管理员」触发器、`plugins` 加 `shared_with_members`、`model_profiles` 加 `shared`。已有主人设为 `admin`。不改写任何数据行。
- 迁移前自动备份(ADR 0005 已有)。
- 回退:旧核心遇到不认识的迁移会拒绝启动(`migrate.ts`:「database has migration N unknown to this version」),不会在多账户数据上以单用户方式运行。要回到 1.x 只能恢复迁移前的备份,升级说明里写清楚。
- 附件目录按账户分子目录的搬迁在同一个版本里做:启动时检查,按数据库行搬,搬完再记标记;中途失败下次启动继续,不删旧文件直到全部搬完。

## 11. 为什么不分库

每个账户一个 SQLite 文件能从结构上杜绝越权,但:备份、迁移、后台任务都要按文件循环;全局状态(嵌入模型、插件、渠道连接)要另开一个库;ADR 0051 已经证明现有的按列隔离加两道检查是可维护的。所以 2.0 继续单库按 `owner_id` 隔离,把检查做严(第 3、6 节)。以后如果出现托管的多租户部署,再单独写 ADR。

## 12. 分 PR 计划(2.0)

1. `feat/accounts-schema`:迁移(第 10 节)、`role` / 停用 / 显示名、最后一个管理员触发器、`/auth/me` 的 `role`、`requireAdmin` 与 `admin_required`;`owner-scope.test.ts` 改用真的第二个账户。
2. `feat/accounts-admin`:邀请码、`/auth/invite/accept`、`/admin/users`、停用 / 删除 / 重置码、登录限流两层;Web 设置页「账户」与登录页的邀请码入口;管理员路由扫描测试。
3. `feat/admin-capabilities`:第 4 节的能力分级(文件夹分配、MCP、插件开放、编码项目、嵌入模型),每项的成员越权用例;外连目标页按账户。
4. `feat/member-secrets`:第 5 节的密钥前缀与引用检查、共享模型配置档。
5. `feat/fair-scheduling`:第 8 节的并发上限与后台任务按账户轮转;两个账户的事件 / 检索隔离测试;附件目录按账户搬迁。
6. 文档与自检:部署指南的「家庭 / 小团队」一节、升级与回退说明、2.0 自检清单(含 Windows 实测项)。

每个 PR 按 CLAUDE.md 的高风险要求写手工验证步骤(数据迁移、安全)。

## 13. 待业主决定

1. **成员能不能用文件和编码工具**。推荐:按第 4 节,成员只能用管理员分配的文件夹,MCP 与编码项目只有管理员能用;理由是这些能力等于服务器的系统权限,家庭场景里成员一般不需要。
2. **账户怎么建**。推荐:只有管理员发邀请码,成员自己设密码;不做公开注册,管理员也不替别人设密码。
3. **共享模型配置档**。推荐:做(第 5.1 节),家庭里最常见的是一个人付费大家用;成员看不到密钥。
4. **管理员能否查看成员数据**。推荐:不能,管理员只管账户;需要帮成员排查时由成员自己导出诊断包。
5. **每个账户同时运行的上限**。推荐:默认 2,管理员可改。
6. **排期**。推荐:本 ADR 确认后,2.0 的实现从第 12 节第 1 个 PR 开始;在此之前 1.x 继续只有一个账户,`trg_owners_single` 保留。
